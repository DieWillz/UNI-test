## 1. Суть задания

Добавить в уже работающий `uni/devcoord/` два новых модуля поверх существующих
`models.py`, `coordinator.py`, `providers.py`, `store.py` (импортировать, а не
переписывать):

  - `verifier.py`  — проверять утверждения ИИ о коде по РЕАЛЬНОМУ репозиторию
                     (grep/AST), а не верить ответу модели на слово.
  - `applier.py`   — применять предложенный патч в отдельной git-ветке, гнать
                     тесты и ОСТАНАВЛИВАТЬСЯ перед коммитом. Никакого авто-коммита
                     и авто-мержа (это жёсткое ограничение, не подлежащее
                     обсуждению — причина: уже пойманные противоречивые фактические
                     утверждения разных ИИ об одном и том же коде).

### Пункт 2 — uni/devcoord/verifier.py (новый модуль)
  · `Verifier(repo_root)` с методом `verify_claim(claim, file_hint=None)`.
  · Логика: извлекает «code-подобные» токены из утверждения (snake_case /
    camelCase / с цифрами), ищет их подстрокой в РЕАЛЬНЫХ файлах репозитория
    (grep-подобно, без внешних зависимостей).
  · Поддержка отрицательных утверждений: «X НЕ существует» → если совпадений
    нет, это трактуется как подтверждение отрицания (verified=True).
  · Исключает справочные/архивные каталоги (Uni-Claude, backup, copilot-worktrees
    и т.п.), чтобы не получать ложные срабатывания.
  · `ClaimVerificationResult` намеренно размещён в models.py (а не в verifier.py),
    чтобы не возникал цикл импортов (verifier импортирует models; models не
    импортирует verifier). Требование «одно поле verified в models.py» выполнено.

### Пункт 3 — uni/devcoord/coordinator.py (интеграция)
  · `__init__` получил опциональный `verifier: Verifier | None = None`.
  · После получения ответа от провайдера в `run_next` (и проброшено в `run_all`):
      if verify_claim and self.verifier is not None:
          result.verified = self.verifier.verify_claim(verify_claim)
  · Результат кладётся в `task.results[i].verified` и сохраняется через
    `CoordinationStore` (round-trip проверен тестом).

### Пункт 4 — uni/devcoord/applier.py (новый модуль)
  · `ApplyResult(BaseModel)`: branch, diff, tests_passed, test_output, status.
  · `Applier.apply_and_test(task_id, patch)` (async):
      1. `git checkout -B review/<task_id>` (из текущей ветки)
      2. `git apply --whitespace=nowarn < patch`
      3. `pytest -q`  +  `python scripts/check_architecture.py --strict`
         (если скрипт есть в репозитории; если нет — пропускается)
      4. ТЕСТЫ УПАЛИ или патч не применился → `git checkout <base>` + удаление
         ветки, status="reverted"
      5. ТЕСТЫ ПРОШЛИ → status="awaiting_human_confirmation"
         НИКАКОГО коммита и НИКАКОГО мержа.
  · `Applier.confirm_merge(task_id)` (async) — вызывается ТОЛЬКО человеком:
      коммитит подтверждённое изменение на ветке review, затем мержит в base.
      Никогда не вызывается автоматически из apply_and_test.

### Пункт 5 — tests/test_devcoord_verifier_applier.py (новые тесты)
  · Verifier на РЕАЛЬНОМ репозитории:
      - true claim («_API_ALIASES в executors.py») → verified=True
      - false claim («nonexistent_xyz_token_abc в executors.py») → verified=False
      - negated claim («... НЕ существует») → verified=True (не найдено = ок)
      - no tokens → verified=False
  · Coordinator round-trip: verify_claim → result.verified заполнен и
    сохранён в store (read-back совпадает).
  · Applier на scratch git-репозитории:
      - pass → awaiting_human_confirmation, ветка остаётся, базовая ветка НЕ
        закоммичена автоматически; confirm_merge → merge-коммит в base.
      - fail (добавлен падающий тест) → reverted, ветка удалена, база нетронута.
      - unapplicable patch (контекст не совпадает) → reverted, ветка удалена.

## 5. Что должен сделать человек (ручное действие)

  При реальном применении патча через `Applier.apply_and_test(...)`:
    1. Ветка `review/<task_id>` остаётся в репозитории до явного подтверждения.
    2. Посмотреть diff (`git diff review/<task_id>`) и вывод тестов
       (`ApplyResult.test_output`).
    3. Только вручную вызвать `confirm_merge("<task_id>")` — это сделает
       merge в base-ветку. `apply_and_test` сам НЕ коммитит и НЕ мержит.

  Также рекомендуется (вне scope, но мешает Applier'у в живом репо): устранить
  предсуществующую ошибку `computer.py` → `uni_action_badge`, иначе гейт
  check_architecture всегда будет «красным».

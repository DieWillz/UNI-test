# UNI — общий handoff для Claude, DeepSeek, Qwen и OpenCode

Дата среза: 2026-07-31

## 1. Зачем передан этот пакет

В проекте существовало несколько параллельных реализаций: корневая, Claude,
DeepSeek и OpenCode. Они разрабатывались с разным пониманием контрактов, поэтому
полное копирование одной реализации поверх другой запрещено.

Цель текущего этапа — не добавить ещё одну функцию, а консолидировать проект в
одну проверяемую систему и после этого довести MVP до end-to-end сценария.

## 2. Единственный источник истины

Канонический продукт находится в `uni/`.

В исходном рабочем каталоге также существуют `Uni-Claude`, `Uni-DeepSeek`,
`Uni-OpenCode`, `Claude`, `backup`, `1` и вложенная копия `uni/uni`. Они намеренно
не включены в архив. Их сравнительные характеристики зафиксированы в
`BUILD_STATUS.md`.

Нельзя:

- создавать ещё одну копию проекта;
- заменять канонический пакет целой модельной веткой;
- импортировать код из архивных каталогов;
- менять публичный контракт без принятого ADR;
- реализовывать работу, назначенную другой роли;
- исправлять архитектурное расхождение локальной несовместимой вариацией.

## 3. Что представляет собой UNI

UNI — локальный модульный автономный агент для управления компьютером.

Целевой цикл:

```text
User goal
  ↓
Agent
  ↓
AgentContext
  ↓
Planner → TaskQueue
  ↓
Action
  ↓
CapabilityRouter
  ↓
Capability → OS / application
  ↓
ActionResult + Observation
  └──────────────→ AgentContext → Planner
```

Lifecycle:

```text
Observe → Think → Plan → Speak → Act → Verify → Recover
```

Цель MVP: пользователь просит открыть Chrome, найти на YouTube видео про LM
Studio, включить первый подходящий результат, проверить воспроизведение и
сообщить об успехе. Временная ошибка должна приводить к retry, неверная стратегия
— к replan, исчерпание восстановления — к запросу помощи пользователя.

## 4. Основные архитектурные принципы

- Python отвечает за исполнение, состояние, ограничения и детерминированную
  логику.
- Markdown хранит роли, skills, workflows и знания.
- LLM используется только для семантических решений и перепланирования.
- Capability не вызывает другую Capability.
- Planner не импортирует конкретные реализации Browser, Computer, Speech или
  Vision.
- Любая попытка действия возвращает единый `ActionResult`.
- Каноническое имя действия имеет формат `capability.action`.
- Все циклы имеют явные условия завершения и ограниченное число повторов.
- Архитектурное решение фиксируется ADR и после принятия обязательно для всех.

## 5. Текущее реальное состояние

Синтаксис канонического Python-кода проверяется успешно, но окружение проекта
ещё не установлено, поэтому полный тестовый запуск пока заблокирован отсутствием
зависимостей.

Известные проблемы:

1. Нет принятого общего контракта для `Action`, `ActionResult`, `Observation`,
   `AgentContext` и `Task`.
2. Planner использует dotted actions, а текущий executor — underscore actions.
3. `depends_on` из ответа LLM не переводится надёжно в сгенерированные `Task.id`.
4. Старый реактивный EventLoop и новый Planner-контур не интегрированы.
5. Registry, executor, working memory и event loop отличаются между модельными
   вариантами.
6. Тесты ожидают несовместимые импорты и типы результатов.
7. Retry, recovery, replan, verification и human-in-the-loop не образуют один
   законченный цикл.

Команда `py -3 scripts/check_architecture.py` должна запускаться после каждого
изменения. Текущий аудит намеренно сообщает конфликт action naming и наличие
вложенной копии исходного пакета.

## 6. Порядок работы

```text
Claude: CORE-001 + draft ROUTER-001
              ↓
Принятие ADR-0004 и ADR-0005 координатором
              ↓
Qwen: CORE-002        DeepSeek: PLAN-001
              \        /
               \      /
        OpenCode: INTEGRATE-001
                    ↓
        Reviewer + tests + audit
                    ↓
             MVP smoke test
```

До принятия зависимого решения нельзя начинать следующий этап.

## 7. Роли и точные результаты

### Claude — Software Architect

Выполняет `CORE-001`. Пишет только архитектурные документы.

Результаты:

- `docs/decisions/ADR-0004-runtime-contracts.md`;
- проект `docs/decisions/ADR-0005-capability-router.md`;
- схемы, инварианты, владение состоянием и async-границы;
- таблица миграции существующих вариантов.

Claude не реализует Python и не добавляет новый framework.

### DeepSeek — Algorithms Engineer

Начинает только после принятия контрактов и router ADR.

Результат: `docs/specs/planner-algorithm.md`, содержащий ID шагов, зависимости,
валидацию плана, retry/replan/escalation, deadlock detection, условия завершения,
псевдокод и тестовые векторы.

DeepSeek не меняет архитектуру и пока не пишет runtime Python.

### Qwen — Python Module Developer

Начинает `CORE-002` только после принятия ADR-0004.

Разрешённые файлы:

- `uni/contracts.py`;
- `tests/unit/test_contracts.py`.

Результат: строгая реализация принятых контрактов и unit-тесты. Остальные модули
не адаптировать — только перечислить будущие точки миграции.

### OpenCode + Nemotron — Lead Implementation Engineer

Сначала предоставляет письменный integration plan, сравнивающий event loop,
agent, registry, executor и memory вариантов.

Реализацию `INTEGRATE-001` начинает только после принятия `CORE-002`,
`ROUTER-001` и `PLAN-001`. Нельзя копировать целую модельную ветку.

## 8. Протокол архитектурного конфликта

Если утверждённый контракт невозможно реализовать:

1. Не менять его молча.
2. Остановить затронутую задачу.
3. Создать change request:
   - проблема;
   - доказательство;
   - затронутые модули;
   - варианты решения;
   - рекомендуемый минимальный вариант.
4. Передать Claude для архитектурной оценки.
5. Получить решение координатора и новый ADR.
6. Только после этого продолжить реализацию.

## 9. Критерии приёмки изменений

Изменение принимается, только если:

- выполнена одна утверждённая задача;
- изменены только разрешённые пути;
- нет новых дубликатов контрактов;
- нет импортов из архивных вариантов;
- тесты задачи проходят;
- `compileall` проходит;
- архитектурный аудит не сообщает новых ошибок;
- Reviewer не обнаружил блокирующих проблем;
- статус и решения обновлены.

Исполнитель не может самостоятельно принять собственную работу.

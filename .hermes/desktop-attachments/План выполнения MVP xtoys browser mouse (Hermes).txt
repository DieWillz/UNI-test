2. ЧТО СТРОИМ (НОВЫЕ файлы, не дублируют существующие)
----------------------------------------------------------------
 2.1  uni/motion/trajectory.py
      — ЧИСТАЯ МАТЕМАТИКА (без GUI/pyautogui), легко тестировать.
      — Берём КАК ЕСТЬ из ТЗ: build_move_path (кубич. Безье + easing
        ease_in_out_cubic + микро-шум «живой руки»), build_wander_path
        (Лиссажу), build_circle_path, MousePath, clamp, _bezier.
      — Только правка импортов под реальный путь (без изменений, код ТЗ
        уже self-contained).

 2.2  uni/motion/driver.py
      — SmoothMouseDriver (адапт ВЕРСИЮ из ТЗ, НО без дублирования клика):
        * move_to/wiggle/wander/circle/drag_to играют Безье-точки через
          pyautogui.moveTo(px, py, _pause=False) + asyncio.sleep(delay).
        * В КОНЕЧНОЙ точке движения — flash бейджа через
          uni.action_badge.get_default_badge().flash_at(x, y, "move"),
          чтобы подпись «UNI» появлялась и при «гулянии», а не только на клике.
        * failsafe: pyautogui.FAILSAFE = True (как в computer.py).
        * НЕ реализуем свой click()/type() — для кликов/ввода сценарий
          использует СУЩЕСТВУЮЩИЙ ComputerCapability (там уже бейдж+блокировки).

 2.3  uni/motion/label.py
      — CursorLabelOverlay (адапт из ТЗ): непрерывно следующий за курсором
        tkinter-оверлей «Uni» (always-on-top, прозрачный). Это ДОПОЛНЯЕТ
        action_badge (который только на клике) — даёт непрерывную «табличку
        Uni» из DoD. НЕ дубликат: action_badge = вспышка на клике,
        CursorLabelOverlay = постоянное сопровождение.
      — _enable_dpi_awareness() (SetProcessDpiAwareness(1)) оставляем —
        нужно, чтобы координаты pyautogui/оверлея совпадали при DPI≠100%.

 2.4  uni/motion/__init__.py — реэкспорт driver/label/trajectory.

 2.5  uni/scenarios/__init__.py — пустой init пакета.

 2.6  uni/scenarios/xtoys.py — ДЕМО-СЦЕНАРИЙ (ПЕРЕПИСАН под реальный код):
      * Запуск: python -m uni --demo xtoys
      * Строит Agent(config), agent.initialize() (браузер/речь готовы).
      * Берёт из agent.capabilities: browser, computer, xtoys, speech.
      * Последовательность:
          1. overlay = CursorLabelOverlay(label=config.demo.mouse.label_text);
             overlay.start(); overlay.show()
          2. speech.speak("Привет! Это мышка Uni. Открываю xtoys...")
          3. xtoys.open()  (через XToysCapability — реальный xtoys.app)
          4. mouse = SmoothMouseDriver(); mouse.wiggle()  (приветствие)
          5. mouse.wander(bounds) — плавно водим «UNI» по вьюпорту/экрану
          6. «погладить игрушки»: для N точек — computer.click(x,y)
             (существующий метод: плавный заезд + бейдж + клик)
          7. xtoys.ramp_intensity(0 → modest → 0) — НО соблюдаем гейт:
             значение ≤ config.capabilities.xtoys.max_intensity (по умолч. 50),
             НЕ вызываем set_verified_physical(True), НЕ включаем
             autonomous_physical. Движение устройства = только UI-слайдер
             (пользователь сам запустил демо → supervised).
          8. speech.speak("Готово! Игрушки поглажены.")
          9. overlay.hide(); overlay.stop()
      * bounds для wander: screen_size из SmoothMouseDriver (весь экран) —
        не пытаемся маппить вьюпорт→экран (ненадёжно при DPI); «гуляние»
        по всему экрану безопаснее и проще.
      * failsafe: оборачиваем в try/except; при pyautogui.FailSafeException
        — overlay.stop() и чистый выход (без краша).

 2.7  tests/test_motion_trajectory.py — ЧИСТЫЕ ЮНИТ-ТЕСТЫ (без GUI):
      * build_move_path((0,0),(800,600),1.0) → points не пусты, финиш ≈ end
      * длина points == длина delays; duration ≈ заявленной
      * build_wander_path/get_circle_path возвращают корректные MousePath
      * distance<1 → возврат одной точки (без деления на 0)
      (Копируем «Проверка 1» из ТЗ как pytest-тест.)

4. ГЕЙТЫ БЕЗОПАСНОСТИ (ОБЯЗАТЕЛЬНО СОХРАНИТЬ)
----------------------------------------------------------------
 🔒 XToys max_intensity: сценарий НЕ поднимает интенсивность выше
    config.capabilities.xtoys.max_intensity (по умолч. 50). Демо-рамп
    идёт 0 → ~20-30 → 0 (скромно, не «максимум»).
 🔒 verified_physical: НЕ вызываем set_verified_physical(True) в демо.
    Устройство двигается только через UI-слайдер xtoys.app, который
    пользователь сам запустил (supervised). Никакого автономного
    физического движения без явного config-флага autonomous_physical.
 🔒 Failsafe: pyautogui.FAILSAFE=True (дублируем из computer.py).
    Увод курсора в левый верхний угол → FailSafeException → overlay.stop()
    + чистый выход (DoD п.2).
 🔒 ESC/стоп мгновенно: не блокируем event loop; tkinter-оверлей в
    отдельном потоке (как в ТЗ и как в action_badge).

7. РИСКИ И РЕШЕНИЯ
----------------------------------------------------------------
 Р1. tkinter/pyautogui/playwright могут отсутствовать в headless-CI.
     Решение: trajectory-тесты не требуют GUI; демо-прогон только локально.
     Импорт label.py/driver.py делаю безопасным (try/except при старте
     оверлея, как в UniActionBadge).

 Р2. Совпадение координат при DPI≠100% (ТЗ упоминает).
     Решение: CursorLabelOverlay._enable_dpi_awareness() + wander по ВСЕМУ
     экрану (screen_size), без маппинга вьюпорт→экран (ненадёжно).

 Р3. Конфликт двух «UNI»-бейджей (action_badge на клике + CursorLabelOverlay
     постоянно). Решение: это ДОПОЛНЯЮЩИЕ индикаторы (вспышка vs сопровождение);
     визуально не конфликтуют. Если пользователю будет «шумно» — отключаем
     action_badge в демо через config.computer.action_badge=False.

 Р4. Переписывание ТЗ-кода под реальный API.
     Решение: trajectory.py берём дословно (он самодостаточен); driver/label
     — адаптируем импорты (uni.motion / uni.action_badge); scenarios/xtoys.py
     — ПЕРЕПИСЫВАЕМ, т.к. ТЗ-версия ссылается на несуществующий
     config.demo.xtoys и BrowserCapability(headless=False) (реальный
     BrowserCapability требует session, а не headless-флаг).

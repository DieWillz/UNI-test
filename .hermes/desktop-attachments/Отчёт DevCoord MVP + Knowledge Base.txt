4. КЛЮЧЕВЫЕ РЕШЕНИЯ
----------------------------------------------------------------
  a) Блокер check_architecture: раньше был 1 error на computer.py
     (импорт uni_action_badge из папки capabilities). После переноса
     файла в uni/action_badge.py и правки импорта гейт чист:
     0 error(s), 0 warning(s).

  b) Промпты советника/критика/исполнителя вынесены в uni/prompts/*.txt
     (Markdown-тексты), Coordinator подгружает их и вставляет advisor
     в инструкции handoff для каждого участника (run_next).

  c) select_participants: адаптирован к реальному ProviderRegistry
     (конфигурации в self.providers.configs.values(), не .providers),
     читает прошлый успех из KnowledgeBase.find_similar_responses,
     сортирует по confidence, фильтрует по бюджету (парсинг api_cost:
     "free"→0.0, "unknown"→0.5, число→float, иначе→1.0).

  d) Aggregator: dedup по md5(content), агрегация с качеством
     (verified 0.4 + tests 0.3 + follows_architecture 0.3), кэш в JSON.

  e) DevPipeline.process_task: реальный цикл — проверка утверждений
     (verifier), агрегация, применение патча (Applier.apply_and_test),
     сохранение ответов в KnowledgeBase, извлечение навыков.

  f) CouncilBridge: строит реальный DevelopmentTask (goal/instructions/
     provider_sequence) из топика совета и делегирует DevPipeline.

  g) CLI confirm: единственный путь merge. Applier.apply_and_test
     НЕ коммитит и НЕ мержит (status=awaiting_human_confirmation,
     ветка review/<id> остаётся). Merge только вручную через
     `python -m uni.devcoord confirm <id> [--repo DIR]`. Базовая ветка
     сохраняется в .uni-dev/review_base_<id>.txt для кросс-процессного
     подтверждения.
